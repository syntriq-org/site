Start with the relationships people recognise

Business users understand customers, agreements, assets and responsibilities. They also understand that relationships carry meaning: a customer holds an agreement; a party operates an asset; a policy applies for a period. A useful application model makes those distinctions explicit.

Without that foundation, a field called owner can mean different things in different screens. An integration may copy the value correctly while losing the business meaning. Syntriq uses ontology identities and explicit contracts to keep that context available.

Connect definitions to behaviour

A model becomes useful when application behaviour refers back to it. A form collects facts for a declared entity. A constraint checks whether those facts are acceptable. A workflow uses a decision contract to choose the next permitted step. A measure identifies the records and time perspective it summarises.

This does not mean every interface can be generated automatically from an ontology. Presentation choices and domain behaviour still need explicit definitions and registered implementations. The benefit is that these pieces have a common reference point.

Expose the model through typed access

GraphQL provides an interface for querying data and supported metadata. Ontology identities, relationships, constraints and temporal context can travel alongside values, giving consumers enough information to interpret what they receive.

Changes should respect those contracts. Renaming a display label is different from changing the meaning of a relationship. Altering a quantity’s unit is different from formatting it. The platform architecture needs to preserve those distinctions across interfaces.

Use an agreement as the connecting example

An agreement form gathers a customer reference, value and effective date. Validation checks required information and compatible quantities. A policy determines whether review is required. The workflow coordinates that review, while the analytical definition determines which agreements count as activated.

If the approval condition changes, the application catalogue can identify the rule, its dependent workflow and the relevant scenarios. The engineer can inspect the connected effects without treating each screen as an unrelated feature.

Make reuse a deliberate boundary

ChargeWeave supplies EV-specific entities and relationships. The generic platform handles supported modelling, constraints, queries and runtime contracts. A reusable component should accept those definitions rather than contain hidden assumptions about charging.

That boundary makes extraction practical: stable contracts and executable examples provide a basis for moving generic mechanisms into Syntriq while preserving domain behaviour in the application package.
